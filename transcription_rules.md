# Транскрипция и диаризация звонков — общая методология

Рабочая связка для расшифровки записей разговоров (`.cap`, `.m4a` и т.п.),
общая для всех проектов, использующих archive-lib.

Личные детали (реальные абсолютные пути, кто прошёл voice-enrollment и когда,
какие конкретно звонки калибровались) сюда не входят — они живут в
`altush_config.md` (gitignored, не часть этого репозитория). Итоговый
`TRANSCRIPTION.md`, который реально читают проекты, собирается из этого файла
плюс `altush_config.md`:

```bash
python3 scripts/build_transcription_doc.py
```

Без `altush_config.md` скрипт всё равно соберёт `TRANSCRIPTION.md` — просто
без секции с личными заметками.

## Транскрипция

`whisper-cli` (whisper.cpp, нативный arm64/Metal) + модель
`whisper-models/ggml-large-v3.bin` относительно корня archive-lib (гитигнорена).
Без ручной чистки текст обычно почти без пунктуации; whisper.cpp регулярно
дублирует смежные куски текста подряд (temperature fallback / возможно
контекстное зацикливание через `--max-context`, не подтверждено) — на
короткой чистой записи это может быть 1–2 места, на длинной и/или шумной
(больше пауз/тихих участков на минуту) может убрать дублированием почти
половину слов. Тяжесть артефакта коррелирует с длиной записи и плотностью
пауз, но точный механизм не проверялся контролируемо.

**Обязательные шаги (не опционально, не только когда дублирование заметно на глаз):**
- Прогонять дедуп текста после транскрипции всегда: точное совпадение смежных
  n-грамм длиной ≥2 слова → схлопывать. Не трогать одиночные повторы (L=1,
  «да да да», «так так так») — это легитимная речь, не баг.
- Сохранять диагностику звонка (whisper stderr-лог с `fallbacks = Np/Mh`,
  `.srt` до дедупа, `diar.json`) в постоянном месте проекта, не в
  `/tmp`-скретчпаде сессии — иначе сравнение артефакта между звонками задним
  числом невозможно. WAV не хранить — исходный файл записи (`.cap`/`.m4a`)
  и так остаётся у пользователя.
- На длинной записи (ориентир: от ~20–30 минут) сначала попробовать
  `whisper-cli -mc/--max-context 0` (обнулить контекст между окнами
  распознавания) — это штатный флаг именно против переноса сбоя декодера
  вперёд по записи, проще и надёжнее, чем ручная нарезка аудио на
  перекрывающиеся фрагменты со сшивкой по таймкодам.

Аудио перед подачей — конвертировать в WAV 16kHz mono через ffmpeg.

## Поиск исходного файла записи

Название папки записей (Cap) не обязательно буквально `Cap` — искать через Spotlight по
имени собеседника, не по предполагаемому пути:

```bash
mdfind -name "<Фамилия>"
```

надёжнее, чем угадывать путь (`find ~/Movies/Cap` и т.п. может не найти реальную папку).

**Ловушка (20.08.2026):** `mdfind` может не найти вообще ничего, даже по точному имени
папки записи (пусто, без ошибки) — Spotlight-индекс не гарантированно покрывает
нестандартные пользовательские каталоги. В этом случае — `find` по времени модификации
за нужный день:
```bash
find ~ -maxdepth 6 -type d -newermt "YYYY-MM-DD 00:00:00" 2>/dev/null
```
(с фильтрацией явного шума вроде `Library/Caches`, `node_modules`, `.git`) — находит
папку по факту недавней записи, даже если её путь не под `~/Movies/`. На этой машине
реальный каталог приложения Cap (`so.cap.desktop`) — `~/Video - cap/` (с пробелом и
дефисом в названии), не `~/Movies/Cap`; папка записи внутри называется по паттерну
`<Display> (Display) YYYY-MM-DD HH.MM AM/PM.cap` — время в названии обычно момент
СТАРТА записи, а не момент, который может фигурировать в разговоре как «Cap
YYYY-MM-DD at HH.MM.SS» (это `pretty_name` из `recording-meta.json`, момент
ЗАВЕРШЕНИЯ/сохранения — искать оба варианта времени, они расходятся на длительность
записи).

## Диагностика перед полным прогоном (обязательно, до транскрипции)

Запись может содержать 1 канал (`audio-input.ogg`) или 2 (`audio-input.ogg` — микрофон,
`system_audio.ogg` — системный звук). Наличие второго канала не гарантирует чистого
разделения по говорящему — оба канала могут содержать смешанный звук обеих сторон
(типично при звонке без наушников: голос собеседника через динамик частично попадает
в микрофон, и наоборот).

**Перед прогоном полного пайплайна:**
1. Транскрибировать (или хотя бы прослушать) первую ~1 минуту КАЖДОГО канала отдельно.
   Если оба канала на этом отрезке дают один и тот же текст — каналы смешаны, гарнитура
   не использовалась (или используется speakerphone/системный вывод без изоляции). Если
   каналы дают разный текст (один явно тише/пустой) — вероятно, гарнитура или раздельный
   захват сработали, можно использовать оба канала как честное разделение по говорящему.
2. По результату первой минуты решить: гнать оба канала параллельно и мёржить по
   таймкодам (если разделение чистое) — или брать один канал (обычно `audio-input.ogg`,
   он ближе к говорящему и полнее) и атрибутировать реплики по смыслу диалога, отдельно
   пометив это в транскрипте (см. пример — звонок с Мурзиным 27.07.2026).
3. На длинном тихом участке (from ~1 минуты и дольше без речи по метру громкости)
   выборочно проверить фрагмент внутри него — не сменились ли параметры записи
   (гарнитура отключилась/подключилась в середине звонка, канал пропал). Длительная
   тишина сама по себе провоцирует галлюцинации whisper (см. кейсы «Редактор субтитров
   А.Семкин…», «Субтитры создавал DimaTorzok») — не принимать их за реальную речь и не
   путать эту причину со сменой параметров записи; спот-чек нужен именно чтобы отличить
   одно от другого.

## Диаризация

sherpa-onnx (arm64-native, ONNX Runtime, без PyTorch) — venv
`sherpa-venv/` относительно корня archive-lib (arm64 python3.11 из
`/opt/homebrew`, НЕ x86_64 `/usr/local` python3.10). Модели и скрипты —
в `sherpa-models/`:

- `run_diarization.py <wav> <out.json> <num_speakers>` — сегментация по спикерам
- `merge_transcript_diarization.py <srt> <diar.json> <out.txt>` — склейка транскрипта
  с диаризацией по таймкодам
- `enroll_voice.py add <имя> <wav> [start end]` — добавить голос в профиль.
  **Границы сегмента для эталона — сверять, не доверять вслепую ни срезу по тексту
  whisper, ни границам диаризованного кластера.** Оба источника границ могут задеть
  чужую реплику на стыке: срез по whisper-таймкодам — потому что whisper может
  захватить хвост/начало соседней реплики в один сегмент; диаризованный кластер —
  потому что у speaker-change есть люфт в несколько секунд, короткие интерджекшены
  (типа «ага») на стыке часто не выделяются в отдельный сегмент, а прилипают к
  соседнему кластеру. Перед enrollment — либо прослушать вырезанный клип, либо
  обрезать его до диапазона первого/последнего whisper-сегмента ВНУТРИ диаризованного
  кластера (не до границ самого кластера) — и обрезать оба края, не только начало.
  Если один и тот же кластер после подрезки всё равно оказался с чужим голосом —
  не подрезать его в третий раз, а взять другой диаризованный сегмент того же
  спикера; лучше сразу подготовить 3–4 кандидата из разных мест записи и дать
  выбрать/прослушать, чем угадывать один клип за раз.
- `enroll_voice.py identify <wav> <diar.json>` — сверить кластеры спикеров с профилями.
  **Ненадёжен для говорящего, которого нет в базе профилей:** скрипт всегда берёт
  argmax по косинусному сходству среди enrolled-профилей и сравнивает с порогом
  (0.5) — порог проверяет только «похоже ли вообще», а не «есть ли лучший
  кандидат за пределами enrolled-набора». При малом числе профилей чужой голос
  может случайно пройти порог и выдать правдоподобный на вид score для неверного
  имени. Результат `identify` для потенциально неenrolled человека — считать
  шумом по умолчанию, подтверждать по содержанию разговора, а не по score.
- `voice_profiles.json` (гитигнорен, там биометрия) — хранит именованные голосовые
  профили; кто именно в них обучен, когда и с каким score — см. `altush_config.md`.

## Почему не WhisperX/pyannote

Не пытаться прогонять WhisperX/pyannote.audio через `python3.10` из `/usr/local`
(x86_64-сборка, работает через Rosetta на M1 Pro) для диаризации.

**Why:** два прогона WhisperX (`--diarize`, `--compute_type int8 --device cpu`)
подряд крашились на нативном уровне — процесс зависал в состоянии
uninterruptible sleep (`UE` в `ps`), `kill -9` не действовал физически, ядро
блокировало убийство. Параллельно зависал `ReportCrash` (до 97% CPU по
несколько минут), пользователь видел зависший крашрепорт на экране. Похоже на
баг взаимодействия ctranslate2/MKL/multiprocessing под Rosetta-эмуляцией (в
логе — предупреждение о leaked semaphore перед зависанием), а не случайность —
воспроизвелось дважды подряд с разными файлами. Также при первой попытке
установка WhisperX подтянула numpy 2.x в ОБЩИЙ python3.10, сломав
`--semantic`/`--hybrid` в RAG-поиске archive-lib для всех проектов (пришлось
откатывать).

**How to apply:** если возникает похожая задача (диаризация, что-то на
PyTorch) на этой машине — сначала проверять, есть ли arm64-native альтернатива
(ONNX Runtime, ggml/whisper.cpp и т.п.), и ставить её в отдельный venv на arm64
python (`/opt/homebrew`), не в общий x86_64 python3.10. Тяжёлые ML-библиотеки —
всегда в изолированный venv, никогда в общее окружение, которым пользуется
RAG-инструментарий archive-lib.

## pyannote.audio 4.0 — когда sherpa-onnx проваливается на смешанном канале

На записях без гарнитуры (оба канала Cap несут смешанный звук обеих сторон —
см. диагностику выше) sherpa-onnx-диаризация может давать почти полностью
несбалансированный результат (один спикер — почти вся запись, другой — считаные
секунды), даже когда разговор реально двусторонний. Наблюдалось дважды
(Мурзин 27.07.2026, Кашин 12.08.2026: 16.8 сек из 43 минут). В этом случае —
переключаться на `pyannote.audio` 4.0 (arm64-native venv, НЕ x86_64 из
«Почему не WhisperX/pyannote» выше — это другой, безопасный путь).

**Установка (venv не сохраняется между сессиями на этой машине — пересобирать
по необходимости):**
```bash
/opt/homebrew/bin/python3.11 -m venv pyannote-venv
source pyannote-venv/bin/activate
pip install pyannote.audio soundfile
```
HF_TOKEN — в `archive-lib/.env` (`HF_TOKEN=...`), модель
`pyannote/speaker-diarization-community-1` (кэш уже может быть в
`~/.cache/huggingface/hub/`).

**Две недокументированные ловушки версии 4.0.7 (обе стоили отдельного прогона
впустую 12.08.2026 — проверять сразу, не через диагностику зависшего процесса):**
- `Pipeline.from_pretrained(...)` по умолчанию НЕ уходит на MPS — без явного
  `pipeline.to(torch.device("mps"))` считает на CPU (в разы медленнее; на
  43-минутной записи CPU не уложился в ~20 минут, MPS — единицы минут).
  Проверять `torch.backends.mps.is_available()` **вне sandbox** — внутри
  sandbox GPU недоступен и проверка ложно вернёт `False`.
- Результат вызова пайплайна — не `Annotation` с `.itertracks()`, а датакласс
  `DiarizeOutput`. Сегменты — через `.serialize()["diarization"]`
  (список `{"start", "end", "speaker"}`, speaker вида `"SPEAKER_00"`).

После этого — тот же `enroll_voice.py identify` (sherpa-venv) и
`merge_transcript_diarization.py` из `sherpa-models/` работают на выходе
pyannote без изменений (тот же JSON-формат `{start, end, speaker}`).

## Видео-верификация диаризации по рамке активного говорящего

Если запись `.cap` — не только звук, но и видео экрана, а звонок шёл в UI,
который подсвечивает рамкой текущего говорящего (Zoom/Meet/Yandex Telemost и
т.п. — плитки участников с зелёной/цветной обводкой у активного микрофона), это
независимый от диаризации источник правды для спорных границ спикеров.
Проверено 20.08.2026 на звонке с 5 диаризованными кластерами, один из которых
(`SPEAKER_02`) оказался склейкой коротких реплик РАЗНЫХ реальных участников, а
не отдельным человеком — без видео это осталось бы неразрешённым `(?)` на
несколько реплик подряд.

**Как вытащить кадр без полного декодирования файла:**
```bash
ffmpeg -y -ss HH:MM:SS -i display.mp4 -vframes 1 -q:v 3 out.jpg
```
`-ss` ДО `-i` — быстрый seek, не полный проход по файлу; на видео в
несколько ГБ извлечение одного кадра занимает доли секунды, независимо от
размера файла. Разрешение обычно избыточное (retina-запись) — `-q:v 3`
достаточно для чтения текста в интерфейсе звонка.

**Три эмпирические находки 20.08.2026:**
- **У рамки есть задержка** (на этом звонке — эмпирически ~3 сек между началом
  реплики по транскрипту и появлением рамки у верного участника). Кадр,
  снятый точно на границе реплики по таймкоду ASR, скорее всего покажет
  ПРЕДЫДУЩЕГО говорящего, а не текущего. Снимать нужно ближе к КОНЦУ реплики
  (или через несколько кадров с шагом в секунды), не к её началу — иначе
  результат выглядит правдоподобно, но систематически смещён на один шаг
  назад и уводит атрибуцию в противоположную сторону (было на этом звонке:
  первая проверка по кадру на самой границе дала неверный вывод, который
  пришлось откатывать после кадра чуть позже).
- **Диаризация может слепить разных людей в один кластер** на участке
  быстрого/хаотичного обмена репликами (перебивания, наложение речи) — тогда
  кластер выглядит как «ещё один участник», которого на самом деле нет; серия
  кадров с шагом в несколько секунд на таком участке может показать рамку,
  последовательно переходящую МЕЖДУ несколькими уже известными участниками —
  это и есть признак склейки, а не нового человека.
- **Записанный экран — это экран пользователя, не обязательно окно звонка.**
  Часть кадров может попасть на другое окно в фокусе (почта, чат, браузер) —
  это не брак, а иногда даже более сильное доказательство: если человек в этот
  момент печатает узнаваемое сообщение в чате, синхронное по смыслу с тем, что
  говорится в транскрипте («я ему просто написал…»), это подтверждает
  атрибуцию содержательнее, чем рамка на плитке.

**Бюджет кадров:** извлечение кадра дешёво по времени, но не по вниманию при
разборе — на практике задача обычно ограничивается небольшим числом кадров за
проход (сколько именно — решается по ситуации с пользователем, не жёстко
задано здесь). Разумная тактика — сначала 1 кадр на каждую спорную границу,
затем (если сигнал неоднозначен или подтверждает задержку рамки) добить
2–3 кадра со сдвигом по времени на самых важных границах, а не размазывать
бюджет тонким слоем по всем сразу.

## GigaAM — второй источник для сверки whisper.cpp

`gigaam` (PyTorch, venv `gigaam-venv/`, arm64 python3.11) — независимый ASR, полезен как
второй источник при сверке транскрипта whisper.cpp (структурно почти не дублирует фразы —
RNNT, не temperature-fallback декодер — но по конкретным словам не всегда точнее, см. историю
сравнений в `apteki_transcription_pipeline` памяти apteki). `gigaam.load_model("v2_rnnt",
device="mps")` — модели `v1_ctc/v1_rnnt/v1_ssl/v2_ctc/v2_rnnt/v2_ssl/ctc/rnnt/ssl/emo`
(не `"v3"` — того имени нет в этом пакете; `v3` из более ранних записей относится к отдельному
`gigaam-mlx`, не установленному в этом venv по состоянию на 19.08.2026).

**Ловушка 1 — PyTorch 2.6+ `weights_only`:** `gigaam/__init__.py` грузит чекпоинт через
`torch.load(model_path, map_location="cpu")` без `weights_only=False`; начиная с PyTorch 2.6
дефолт `weights_only` стал `True`, и загрузка падает `UnpicklingError` на
`omegaconf.dictconfig.DictConfig`. Обход — патчить `torch.load` в вызывающем скрипте
(`functools.partial(torch.load, weights_only=False)`) до импорта `gigaam`, не трогая
site-packages. Источник чекпоинта — сам gigaam-репозиторий (доверенный), не сторонний файл.

**Ловушка 2 — `transcribe_longform` требует gated HF-репо:** встроенная VAD-сегментация внутри
`transcribe_longform` тянет `pyannote/voice-activity-detection` — ОТДЕЛЬНЫЙ гейтед репозиторий
от `pyannote/speaker-diarization-community-1` (использован для диаризации выше); доступ на
HuggingFace гейтится per-репозиторий, а не по аккаунту — токен, рабочий для диаризации, может
не иметь доступа к VAD-репо (`GatedRepoError: 403`). По пути всплывает и старая проблема с
`use_auth_token=`→`token=` (см. ловушки pyannote.audio 4.0.7 выше) — `gigaam/vad_utils.py`
всё ещё вызывает `Pipeline.from_pretrained(..., use_auth_token=...)`, нужен тот же monkey-patch
классметода перед вызовом, если вообще пытаться пройти этот путь.

**Обход (работает без доступа к гейтед-VAD-репо):** не звать `transcribe_longform` — нарезать
WAV на фиксированные чанки (`ffmpeg -f segment -segment_time 20 -c copy`, порог короткой
`model.transcribe()` — 25 сек, `LONGFORM_THRESHOLD` в `gigaam/model.py`) и транскрибировать
каждый чанк `model.transcribe(chunk_path)` по отдельности. Дедуп после склейки — того же
порядка, что у whisper.cpp на той же записи (проверено на звонке 19.08.2026: 0,32% vs 0,21%).
Минус — жёсткая нарезка не учитывает паузы речи (в отличие от VAD), возможен обрыв слова на
границе чанка; на выборочной проверке 19.08.2026 заметных потерь не найдено, но системно не
измерялось. Разбор аномалии — `ИИ_самосовершенствование_проекта.md` (sect-lost), запись
2026-08-19 `[apteki]`.

## Confidence-флаг whisper.cpp / Parakeet / GigaAM — пилотный шаг сверки

**Статус: пилот, не обязательный шаг пайплайна** (мини-регрессия n=3, не откалибровано
статистически — полный разбор апробации `apteki/распознавание_речи_diarization_альтернативы.md`,
раздел «Результат: мини-регрессия + confidence», 20.08.2026).

**Что делать:** добавить `-ojf` к обычному вызову `whisper-cli` (сейчас в практике не
используется вообще) и прогнать `scripts/flag_low_confidence.py out.json` по результату:

```bash
whisper-cli -m whisper-models/ggml-large-v3.bin -f audio.wav -l ru -ojf -of out -np
python3 scripts/flag_low_confidence.py out.json --threshold 0.6
```

Печатает токены с `p < 0.6` вместе с контекстом — список кандидатов на ручную сверку, не
автоматическую правку. На известных воспроизведённых ошибках («мэров»/МРов, «вези
на»/Мурзина) точка ошибки давала `p` 0.05–0.25 против фона 0.85–1.0 — сигнал реальный, но
даёт и ложноположительные (пунктуация, границы фраз) — не фильтровать вслепую, смотреть
контекст.

**Ограничение — whisper.cpp non-determinism.** Одна и та же ошибка на одном и том же
аудио не обязательно повторится при повторном прогоне (нет видимого флага seed в
`whisper-cli --help` этой версии) — подтверждено на клипе «кастировать»: два повторных
прогона дали верное слово с высокой уверенностью там, где оригинальный прогон дал
уверенно неверное. Confidence-флаг на **одном** прогоне whisper — не гарантия поимки,
только смещение вероятности.

**Parakeet TDT v3** (`ggml-org/parakeet-GGUF`, файл `ggml-parakeet-tdt-0.6b-v3-f16.bin` —
**не** `cstr/parakeet-tdt-0.6b-v3-GGUF`, тот конвертер `parakeet-cli` не грузит, «failed to
load Parakeet model» без пояснений) технически стабилен, `-ps` даёt те же поля `p`/`plog`
на уровне сабвордов, сигнал того же типа. **Не даёт устойчивого преимущества над GigaAM**
на этом наборе (в одном из трёх случаев совпал с ошибкой whisper независимо, в двух —
ближе к правде) — не добавлять как обязательный третий прогон поверх GigaAM, лишняя
стоимость без доказанной пользы.

GigaAM confidence не публичный API (`RNNTGreedyDecoding` делает argmax и не возвращает
softmax) — извлекается патчем декодера, пример — `gigaam_confidence.py` в
`archive-lib/call-logs/2026-08-20-accuracy-regression/`.

**Уточнение на реальном звонке (32 мин, 2 канала, 20.08.2026, разбор — `apteki/
распознавание_речи_diarization_альтернативы.md`, раздел «Интеграция инструментов…»):**
per-token confidence НЕ масштабируется на целую запись без второго фильтра — порог
p<0.5 дал 543 флага на одном канале за 32 минуты (нечитаемо), p<0.2 — всё ещё 152 на
двух каналах. Сужение до токенов-начала слова не помогло (спонтанная речь сама по себе
даёт много локальных провалов уверенности без ошибки). **Практический вывод:**
confidence-флаг — вспомогательный сигнал в паре со вторым источником (см. ниже), не
самостоятельный список для целого звонка.

## Автоматический фильтр галлюцинаций whisper.cpp на тишине — GigaAM как проверка

**Статус: рекомендуется как стандартный шаг** (не пилот) — на реальном 32-минутном
звонке 17.08.2026 нашёл 13 подряд поддельных 30-секундных сегментов на одном канале
(один блок — 5 сегментов подряд, 2.5 минуты чистой выдумки), GigaAM дал пустую строку
на всех 13 таймкодах — 13 из 13, без единого ложноположительного.

**Механика:** whisper.cpp на длинной тишине (собеседник слушает, не говорит) вместо
пустого сегмента иногда галлюцинирует одну из нескольких фиксированных фраз-артефактов
обучающих данных — `"Продолжение следует..."`, `"Субтитры создавал DimaTorzok"`,
`"Субтитры сделал DimaTorzok"`, `"Редактор субтитров А.Семкин Корректор А.Егорова"` и
вариации. Список не исчерпывающий — пополнять по мере находок. GigaAM на тишине
структурно не подвержен этому (даёт пустую строку, не выдумывает текст).

**Уточнение (20.08.2026, встреча 18→3 участников, `call-logs/2026-08-17-team-meeting/`):**
не только на тишине в хвосте записи — 3 из 14 найденных на этом звонке галлюцинаций
случились посреди активного разговора (в паузах между репликами участников, не только
на длинной финальной тишине). Фильтр (фраза + пустой GigaAM на том же таймкоде) сработал
одинаково надёжно независимо от позиции — сканировать всю запись целиком, не только
хвост.

**Что делать:** после транскрипции — прогнать регэксп по фразам-артефактам, для каждого
совпадения сверить с GigaAM-транскриптом того же таймкода (уже должен быть под рукой как
второй источник); если GigaAM пуст на этом участке — сегмент можно удалять
автоматически, без прослушивания:

```python
import re
HALLUC_RE = re.compile(r'субтитры|продолжение следует|редактор субтитров', re.IGNORECASE)
# сегмент — кандидат на удаление, если HALLUC_RE.search(text) И GigaAM пуст на том же таймкоде
```

## Интеграция инструментов — решающее дерево (не «прогонять всё всегда»)

Полный разбор и обоснование каждого пункта — `apteki/распознавание_речи_diarization_
альтернативы.md`, раздел «Интеграция инструментов + разбор реального ранее
нерасшифрованного звонка» (20.08.2026).

1. **Всегда:** диагностика первых 60 сек каждого канала (уже было правилом). Чистое
   разделение → пропустить диаризацию и видео-верификацию, они не нужны и стоят дороже,
   чем дают на таком звонке.
2. **whisper.cpp `-mc 0` на каждый канал отдельно.**
3. **GigaAM вторым источником — в первую очередь как фильтр галлюцинаций** (см. выше),
   отдельно — сверка спорных слов.
4. **Confidence-флаг** — точечно, там, где whisper и GigaAM всё равно расходятся, не по
   всему транскрипту.
5. **pyannote / `video_speaker_border.py`** — только если шаг 1 показал смешанные
   каналы или участников 3+. `video_speaker_border.py` дополнительно требует окно звонка
   на весь экран — на плавающем неразвёрнутом окне калибровка почти не срабатывает (см.
   `apteki_video_speaker_border_tool.md` в памяти apteki, лимитация от 20.08.2026). На
   встречах с 3+ участниками и меняющимся составом **использовать оба вместе, не
   выбирать один** — на реальной встрече (20.08.2026, 18→3 участников) video-верификация
   пропустила 41% записи (смена раскладки), pyannote в этом же промежутке продолжал
   разделять голоса (анонимно, без имён) — методы дополняют, не дублируют друг друга.
   Merge-логика (приоритет video при покрытии ≥40%, иначе pyannote-кластер, иначе
   «неизвестно») — `merge_attribution.py` в `call-logs/2026-08-17-team-meeting/`.
   Отдельно: pyannote `num_speakers=auto` ненадёжен на коротких перекрывающихся репликах
   (открытие встречи, общие приветствия) — выродился в 1 кластер на 158-сек фрагменте с
   несколькими разными голосами подряд; на более длинных репликах (21 мин) дал разумные
   4 кластера. На открывающих 1–2 минутах — задавать `num_speakers` вручную, если состав
   известен, не полагаться на auto-detect.
6. **Parakeet** — не входит в обязательный набор (нет доказанного преимущества над
   GigaAM на мини-регрессии выше).
