# Транскрипция и диаризация звонков — общая методология

Рабочая связка для расшифровки записей разговоров (`.cap`, `.m4a` и т.п.),
общая для всех проектов, использующих archive-lib.

Личные детали (реальные абсолютные пути, кто прошёл voice-enrollment и когда,
какие конкретно звонки калибровались) сюда не входят — они живут в
`altush_config.md` (gitignored, не часть этого репозитория). Итоговый
`TRANSCRIPTION.md`, который реально читают проекты, собирается из этого файла
плюс `altush_config.md`:

```bash
python3 scripts/build_transcription_doc.py
```

Без `altush_config.md` скрипт всё равно соберёт `TRANSCRIPTION.md` — просто
без секции с личными заметками.

## Транскрипция

`whisper-cli` (whisper.cpp, нативный arm64/Metal) + модель
`whisper-models/ggml-large-v3.bin` относительно корня archive-lib (гитигнорена).
Без ручной чистки текст обычно почти без пунктуации; whisper.cpp регулярно
дублирует смежные куски текста подряд (temperature fallback / возможно
контекстное зацикливание через `--max-context`, не подтверждено) — на
короткой чистой записи это может быть 1–2 места, на длинной и/или шумной
(больше пауз/тихих участков на минуту) может убрать дублированием почти
половину слов. Тяжесть артефакта коррелирует с длиной записи и плотностью
пауз, но точный механизм не проверялся контролируемо.

**Обязательные шаги (не опционально, не только когда дублирование заметно на глаз):**
- Прогонять дедуп текста после транскрипции всегда: точное совпадение смежных
  n-грамм длиной ≥2 слова → схлопывать. Не трогать одиночные повторы (L=1,
  «да да да», «так так так») — это легитимная речь, не баг.
- Сохранять диагностику звонка (whisper stderr-лог с `fallbacks = Np/Mh`,
  `.srt` до дедупа, `diar.json`) в постоянном месте проекта, не в
  `/tmp`-скретчпаде сессии — иначе сравнение артефакта между звонками задним
  числом невозможно. WAV не хранить — исходный файл записи (`.cap`/`.m4a`)
  и так остаётся у пользователя.
- На длинной записи (ориентир: от ~20–30 минут) сначала попробовать
  `whisper-cli -mc/--max-context 0` (обнулить контекст между окнами
  распознавания) — это штатный флаг именно против переноса сбоя декодера
  вперёд по записи, проще и надёжнее, чем ручная нарезка аудио на
  перекрывающиеся фрагменты со сшивкой по таймкодам.

Аудио перед подачей — конвертировать в WAV 16kHz mono через ffmpeg.

## Поиск исходного файла записи

Название папки записей (Cap) не обязательно буквально `Cap` — искать через Spotlight по
имени собеседника, не по предполагаемому пути:

```bash
mdfind -name "<Фамилия>"
```

надёжнее, чем угадывать путь (`find ~/Movies/Cap` и т.п. может не найти реальную папку).

## Диагностика перед полным прогоном (обязательно, до транскрипции)

Запись может содержать 1 канал (`audio-input.ogg`) или 2 (`audio-input.ogg` — микрофон,
`system_audio.ogg` — системный звук). Наличие второго канала не гарантирует чистого
разделения по говорящему — оба канала могут содержать смешанный звук обеих сторон
(типично при звонке без наушников: голос собеседника через динамик частично попадает
в микрофон, и наоборот).

**Перед прогоном полного пайплайна:**
1. Транскрибировать (или хотя бы прослушать) первую ~1 минуту КАЖДОГО канала отдельно.
   Если оба канала на этом отрезке дают один и тот же текст — каналы смешаны, гарнитура
   не использовалась (или используется speakerphone/системный вывод без изоляции). Если
   каналы дают разный текст (один явно тише/пустой) — вероятно, гарнитура или раздельный
   захват сработали, можно использовать оба канала как честное разделение по говорящему.
2. По результату первой минуты решить: гнать оба канала параллельно и мёржить по
   таймкодам (если разделение чистое) — или брать один канал (обычно `audio-input.ogg`,
   он ближе к говорящему и полнее) и атрибутировать реплики по смыслу диалога, отдельно
   пометив это в транскрипте (см. пример — звонок с Мурзиным 27.07.2026).
3. На длинном тихом участке (from ~1 минуты и дольше без речи по метру громкости)
   выборочно проверить фрагмент внутри него — не сменились ли параметры записи
   (гарнитура отключилась/подключилась в середине звонка, канал пропал). Длительная
   тишина сама по себе провоцирует галлюцинации whisper (см. кейсы «Редактор субтитров
   А.Семкин…», «Субтитры создавал DimaTorzok») — не принимать их за реальную речь и не
   путать эту причину со сменой параметров записи; спот-чек нужен именно чтобы отличить
   одно от другого.

## Диаризация

sherpa-onnx (arm64-native, ONNX Runtime, без PyTorch) — venv
`sherpa-venv/` относительно корня archive-lib (arm64 python3.11 из
`/opt/homebrew`, НЕ x86_64 `/usr/local` python3.10). Модели и скрипты —
в `sherpa-models/`:

- `run_diarization.py <wav> <out.json> <num_speakers>` — сегментация по спикерам
- `merge_transcript_diarization.py <srt> <diar.json> <out.txt>` — склейка транскрипта
  с диаризацией по таймкодам
- `enroll_voice.py add <имя> <wav> [start end]` — добавить голос в профиль.
  **Границы сегмента для эталона — сверять, не доверять вслепую ни срезу по тексту
  whisper, ни границам диаризованного кластера.** Оба источника границ могут задеть
  чужую реплику на стыке: срез по whisper-таймкодам — потому что whisper может
  захватить хвост/начало соседней реплики в один сегмент; диаризованный кластер —
  потому что у speaker-change есть люфт в несколько секунд, короткие интерджекшены
  (типа «ага») на стыке часто не выделяются в отдельный сегмент, а прилипают к
  соседнему кластеру. Перед enrollment — либо прослушать вырезанный клип, либо
  обрезать его до диапазона первого/последнего whisper-сегмента ВНУТРИ диаризованного
  кластера (не до границ самого кластера) — и обрезать оба края, не только начало.
  Если один и тот же кластер после подрезки всё равно оказался с чужим голосом —
  не подрезать его в третий раз, а взять другой диаризованный сегмент того же
  спикера; лучше сразу подготовить 3–4 кандидата из разных мест записи и дать
  выбрать/прослушать, чем угадывать один клип за раз.
- `enroll_voice.py identify <wav> <diar.json>` — сверить кластеры спикеров с профилями.
  **Ненадёжен для говорящего, которого нет в базе профилей:** скрипт всегда берёт
  argmax по косинусному сходству среди enrolled-профилей и сравнивает с порогом
  (0.5) — порог проверяет только «похоже ли вообще», а не «есть ли лучший
  кандидат за пределами enrolled-набора». При малом числе профилей чужой голос
  может случайно пройти порог и выдать правдоподобный на вид score для неверного
  имени. Результат `identify` для потенциально неenrolled человека — считать
  шумом по умолчанию, подтверждать по содержанию разговора, а не по score.
- `voice_profiles.json` (гитигнорен, там биометрия) — хранит именованные голосовые
  профили; кто именно в них обучен, когда и с каким score — см. `altush_config.md`.

## Почему не WhisperX/pyannote

Не пытаться прогонять WhisperX/pyannote.audio через `python3.10` из `/usr/local`
(x86_64-сборка, работает через Rosetta на M1 Pro) для диаризации.

**Why:** два прогона WhisperX (`--diarize`, `--compute_type int8 --device cpu`)
подряд крашились на нативном уровне — процесс зависал в состоянии
uninterruptible sleep (`UE` в `ps`), `kill -9` не действовал физически, ядро
блокировало убийство. Параллельно зависал `ReportCrash` (до 97% CPU по
несколько минут), пользователь видел зависший крашрепорт на экране. Похоже на
баг взаимодействия ctranslate2/MKL/multiprocessing под Rosetta-эмуляцией (в
логе — предупреждение о leaked semaphore перед зависанием), а не случайность —
воспроизвелось дважды подряд с разными файлами. Также при первой попытке
установка WhisperX подтянула numpy 2.x в ОБЩИЙ python3.10, сломав
`--semantic`/`--hybrid` в RAG-поиске archive-lib для всех проектов (пришлось
откатывать).

**How to apply:** если возникает похожая задача (диаризация, что-то на
PyTorch) на этой машине — сначала проверять, есть ли arm64-native альтернатива
(ONNX Runtime, ggml/whisper.cpp и т.п.), и ставить её в отдельный venv на arm64
python (`/opt/homebrew`), не в общий x86_64 python3.10. Тяжёлые ML-библиотеки —
всегда в изолированный venv, никогда в общее окружение, которым пользуется
RAG-инструментарий archive-lib.

## pyannote.audio 4.0 — когда sherpa-onnx проваливается на смешанном канале

На записях без гарнитуры (оба канала Cap несут смешанный звук обеих сторон —
см. диагностику выше) sherpa-onnx-диаризация может давать почти полностью
несбалансированный результат (один спикер — почти вся запись, другой — считаные
секунды), даже когда разговор реально двусторонний. Наблюдалось дважды
(Мурзин 27.07.2026, Кашин 12.08.2026: 16.8 сек из 43 минут). В этом случае —
переключаться на `pyannote.audio` 4.0 (arm64-native venv, НЕ x86_64 из
«Почему не WhisperX/pyannote» выше — это другой, безопасный путь).

**Установка (venv не сохраняется между сессиями на этой машине — пересобирать
по необходимости):**
```bash
/opt/homebrew/bin/python3.11 -m venv pyannote-venv
source pyannote-venv/bin/activate
pip install pyannote.audio soundfile
```
HF_TOKEN — в `archive-lib/.env` (`HF_TOKEN=...`), модель
`pyannote/speaker-diarization-community-1` (кэш уже может быть в
`~/.cache/huggingface/hub/`).

**Две недокументированные ловушки версии 4.0.7 (обе стоили отдельного прогона
впустую 12.08.2026 — проверять сразу, не через диагностику зависшего процесса):**
- `Pipeline.from_pretrained(...)` по умолчанию НЕ уходит на MPS — без явного
  `pipeline.to(torch.device("mps"))` считает на CPU (в разы медленнее; на
  43-минутной записи CPU не уложился в ~20 минут, MPS — единицы минут).
  Проверять `torch.backends.mps.is_available()` **вне sandbox** — внутри
  sandbox GPU недоступен и проверка ложно вернёт `False`.
- Результат вызова пайплайна — не `Annotation` с `.itertracks()`, а датакласс
  `DiarizeOutput`. Сегменты — через `.serialize()["diarization"]`
  (список `{"start", "end", "speaker"}`, speaker вида `"SPEAKER_00"`).

После этого — тот же `enroll_voice.py identify` (sherpa-venv) и
`merge_transcript_diarization.py` из `sherpa-models/` работают на выходе
pyannote без изменений (тот же JSON-формат `{start, end, speaker}`).
